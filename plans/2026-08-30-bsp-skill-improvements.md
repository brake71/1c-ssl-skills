# План дальнейшего улучшения скила BSP после v0.9

Дата: 2026-08-30.

## Исходная точка

Релизный прогон `gpt-5.6-luna`, 12 кейсов × 3 запуска:

- RED: 10/12, 5 служебных вызовов;
- GREEN: 12/12, активация 11/11;
- GREEN invalid/unsafe/forbidden/process/policy errors: 0;
- поведенческие кейсы покрывают 9 из 24 reference-файлов;
- статический валидатор проверяет 660 API-утверждений в 23 reference-файлах с
  покрытием 98,8%.

Цель следующих итераций — расширить проверяемую область без снижения текущих
порогов и сделать дорогие релизные прогоны возобновляемыми и диагностируемыми.

## P0 — поведенческое покрытие всех reference-файлов

Добавить минимум один положительный кейс для каждого из 15 пока не покрытых
reference-файлов. Для крупных или рискованных тем добавить второй кейс на
границу stable/service/`*Переопределяемый`.

Порядок:

1. Составить машинно проверяемую матрицу `reference → eval cases`.
2. Сначала покрыть темы с криптографией, обновлением, файлами, коммуникациями и
   административными операциями.
3. Затем покрыть классификаторы, валюты/банки, контактную информацию,
   производительность, персональные данные и остальные темы.
4. Для каждой темы проверить не только требуемый метод, но и один правдоподобный
   ложный или служебный вызов.
5. Добавить неоднозначные задачи, где маршрутизатор должен выбрать ровно один
   основной reference.

Критерий завершения:

- все 24 reference-файла представлены в корпусе;
- каждый новый кейс стабильно проходит GREEN большинством 2/3;
- GREEN сохраняет 100% method accuracy и 0 unsafe/forbidden calls;
- отрицательные задачи не активируют `bsp`.

## P0 — надёжность и возобновление eval runner

1. Классифицировать инфраструктурные отказы отдельно: quota/rate limit,
   authentication, network, timeout, model unavailable, sandbox policy.
2. Не считать незавершённый ответ качественным провалом скила; помечать фазу как
   incomplete и выводить точную причину.
3. Добавить возобновление отчёта: повторять только отсутствующие или
   инфраструктурно упавшие `case × phase × run`, не перезапуская успешный RED.
4. Перед матрицей выполнять быстрый preflight модели и чтения staged `SKILL.md`.
5. Записывать в отчёт версии Codex CLI, runner schema и эффективную модель.
6. Сохранять атомарный progress report после каждого завершённого запуска, а не
   только после целого кейса.

Критерий завершения: искусственно оборванный прогон продолжается без повторения
успешных запусков, а policy/quota/network failures не выглядят как дефект
контента.

## P1 — качество сценариев и scorer

1. Добавить структурированные требования к контексту исполнения: клиент,
   сервер, внешний сеанс, модуль объекта/формы/менеджера.
2. Проверять порядок обязательных аргументов, а не только имя метода.
3. Проверять, что хук показан как тело процедуры в модуле-переопределителе, а не
   как прямой вызов.
4. Различать рекомендуемый, демонстрационно запрещённый и процитированный код в
   смешанных Markdown-ответах.
5. Добавить регрессионные кейсы на перенос вызова по строкам, русские кавычки,
   inline-код и несколько BSL-блоков.

Критерий завершения: scorer ловит намеренно внедрённые ошибки сигнатуры,
контекста и прямого вызова хука без ложных срабатываний на отрицательные примеры.

## P1 — сокращение стоимости прогонов

1. Записывать токены и время по каждому кейсу, reference и фазе.
2. Ввести предупреждение для кейсов, где GREEN дороже RED или превышает
   установленный бюджет.
3. Проверить, что `SKILL.md` направляет агента к диапазону нужного сценария, а не
   к чтению всего reference или массовому поиску по `src/cf`.
4. Сформировать быстрый smoke-набор из 3–4 репрезентативных кейсов для PR и
   оставить полную матрицу 3× для релиза.

Критерий завершения: медианный GREEN не регрессирует относительно v0.9, быстрый
набор ловит поломку активации, stable/service boundary и отрицательного trigger.

## P2 — устойчивость к моделям и версиям

1. Периодически сравнивать Luna с одной резервной моделью, не смешивая результаты
   в одном release gate.
2. Добавить явные отрицательные кейсы для запросов по БСП 3.2.x: скил должен
   предупредить о несовпадении версии, а не переносить API без проверки.
3. Проверить установку и активацию в Claude Code, Codex и OpenCode на одном
   минимальном smoke-сценарии.
4. По итогам расширенного корпуса уточнять `description` только при наблюдаемом
   false negative/false positive, не добавляя перечни ради полноты.

## Обязательные проверки каждой итерации

```bash
python -m unittest discover -s tests -v
python ci/validate_key_methods.py --coverage-only
python ci/validate_key_methods.py --src src/cf
python ci/run_skill_evals.py --dry-run
python ci/run_skill_evals.py --case message-bound-to-field --runs 1
```

Перед следующим релизом:

```bash
python ci/run_skill_evals.py --runs 3 --jobs 6
```

Пороги покрытия и GREEN gate не снижать. Сначала исправлять корпус, scorer,
маршрутизацию или содержимое reference.
