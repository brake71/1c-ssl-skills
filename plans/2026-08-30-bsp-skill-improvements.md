# План улучшения скила BSP после v0.11

План актуализирован по состоянию релиза v0.11. Статусы относятся к текущей
реализации: `Done` — критерий закрыт, `Partial` — часть уже реализована,
`Next` — остаётся выполнить.

## Done — поведенческое покрытие references

По CHANGELOG v0.11 все 24 reference-файла имеют поведенческое покрытие.
Матрица `evals/reference-matrix.json` связывает references с eval cases и
показывает неприкреплённые сценарии отдельно. В корпусе 27 сценариев; полный
релизный прогон дал GREEN 27/27 и активацию 26/26, без invalid/unsafe/forbidden/
process/policy errors.

Дальше поддерживать покрытие при изменении корпуса: у каждого из 24 файлов в
матрице должен оставаться хотя бы один существующий сценарий; новые или
перенесённые кейсы синхронно отражать в матрице. При расширении корпуса
проверять границы публичного API, служебных методов и хуков, а не только
положительный вызов.

**Критерий сохранения:** `python ci/run_skill_evals.py --dry-run` проходит,
матрица содержит ровно актуальные 24 reference-файла и все перечисленные case
IDs существуют в корпусе.

## Done — надёжность и возобновление eval runner

По CHANGELOG v0.10 runner поддерживает `--resume`, атомарно сохраняет прогресс
после каждого `case × phase × run` и отделяет инфраструктурные ошибки от
ошибок качества ответа. Успешные и качественно проваленные запуски не
повторяются при возобновлении; повторяются отсутствующие, незавершённые и
инфраструктурно упавшие.

**Критерий сохранения:** unit-тесты подтверждают возобновление без повтора
завершённых запусков и классификацию инфраструктурных ошибок отдельно от
результата качества.

## Done — 100% API claims coverage во всех 24 references

Валидатор исключает из знаменателя только явно неклассифицируемые имена
(платформенные namespace, типы метаданных и локальные переменные), а не
считает их пропущенными API claims. Порог по умолчанию поднят до 100%, минимум
покрытия — 24 reference-файла; минимум claims сохранён. Навигационный файл
`fundamentals.md` содержит реальный проверяемый вызов вместо placeholder.

**Критерий сохранения:** `python ci/validate_key_methods.py --coverage-only`
показывает 100,0% eligible claims и 24/24 файлов; `python
ci/validate_key_methods.py --src src/cf` проходит по локальной выгрузке. Любой
eligible claim, который не извлечён или не подтверждён, должен снижать coverage
или приводить к semantic error.

## Partial — scorer: разделение текстовых и кодовых требований

Scorer уже извлекает BSL-блоки, исключает явно отрицательные примеры, сверяет
требуемые/запрещённые паттерны, проверяет существование известных методов и
помечает прямые вызовы служебных методов и модулей `*Переопределяемый` как
unsafe. Поля `required_code_patterns` и `forbidden_code_patterns` добавлены для
проверок, которые должны совпадать только с рекомендуемым исполняемым BSL-кодом;
`required_code_block_patterns` требует разные шаги в разных исполняемых
fenced-блоках. Тесты проверяют порядок аргументов, директиву контекста,
hook-реализацию и защиту от совпадений в прозе/отрицательном блоке.
Предупреждение не вызывать hook больше не исключает следующий корректный блок
его реализации. Eval-кейс печати требует BSL-кодом оба шага регистрации:
добавить менеджер в `ОбъектыПечати` и включить обработчик в модуле менеджера.
Два существующих кейса
уже переведены на code-specific assertions. Для положительных scoped-кейсов GREEN
теперь также требуется наблюдаемое чтение именно назначенного reference; отчёт
показывает reference-read rate, а GREEN gate требует 100% на уровне scoped
case majorities: каждый такой кейс должен прочитать назначенный reference в
большинстве запусков. Отдельный запуск без чтения сам по себе не проходит.
Пути reference
распознаются как относительные, так и абсолютные; версия отчёта повышена до 3,
чтобы `--resume` не переиспользовал результаты со старой семантикой.

Первый полный GREEN-прогон 27 кейсов × 3 на `gpt-6-luna medium` выявил
повторяемый false negative в распознавании кода: запрет прямого вызова hook,
стоящий **после** правильного BSL-блока, скрывал последний блок от code scorer.
Добавлена симметричная обработка контекста после code fence и регрессионный
тест; кодовый паттерн печати по-прежнему требует обе реализации.

В последующих точечных GREEN-прогонах `print-object-registration` и
`message-bound-to-field` прошли по majority (каждый 2/3), с чтением назначенного
reference в большинстве запусков. Полный прогон после этих исправлений ещё
нужен; его актуальные результаты описаны ниже.

Ограничение: кодовые требования — regex seam для конкретных кейсов, не общий
анализатор BSL-сигнатур и контекста. Общий парсер пока не проверяет число
аргументов, типы и семантику каждого вызова.

## v0.12 — выпуск по решению пользователя с известным quality debt

Текущая база — `v0.11`. Выпуск v0.12 готовится несмотря на провал поведенческого
GREEN gate; это осознанная уступка release gate, не изменение и не снижение его
порогов. Ограничение обязательно отразить в changelog и описании GitHub Release.

Полный RED/GREEN-прогон 27 кейсов × 3 уже выполнен на той же модели. Он
**не прошёл release gate**: GREEN 25/27, reference-read 25/26 (96,2%),
forbidden hits 2; activation 26/26, invalid/unsafe/process/policy/infrastructure
ошибок нет. RED: 14/27. Run-level причины сосредоточены в двух кейсах:
`message-bound-to-field` ни разу не прочитал `base-common.md`, во всех трёх
ответах пропустил требуемый API БСП, дважды предложил запрещённый объект
платформы; `print-object-registration` выполнил строгую кодовую проверку только
в 1 из 3 запусков, хотя назначенный reference читал во всех трёх. Отчёт:
`.tmp/gpt6-luna-medium-v0.12-full-3x.json`.

После первого полного прогона применены следующие исправления: маршрут
сообщений с привязкой к полю явно назначает `base-common.md` основным reference;
reference уточняет выбор `КлючДанных`/`Поле`/`ПутьКДанным` и исключает подмену
запрошенного API БСП платформенным объектом; eval проверяет это объяснение.
Задача печати просит два отдельных BSL-фрагмента без подсказки точных имён
процедур. Code scorer сохраняет реализацию hook, если пояснение о запрете
прямого вызова находится до или после её fenced-блока. Unit-регрессии проходят.

Точечный GREEN `message-bound-to-field` (`gpt-6-luna medium`, 3 повтора)
прошёл по majority: 2/3, с majority reference-read; отчёт
`.tmp/gpt6-luna-medium-v0.12-message-ref-followup-3x.json`. Code-review выявил,
что combined regex для печати мог принять две одноимённые процедуры внутри
одного fenced-блока. В scorer добавлено `required_code_block_patterns`, которое
требует разные необходимые шаги в разных исполняемых блоках; unit-тест проверяет,
что один блок с двумя одноимёнными процедурами не проходит. Повторный GREEN
`print-object-registration` после ужесточения дал 0/3: модели читали reference,
но не предъявили обе валидные реализации в требуемых отдельных блоках. Отчёт:
`.tmp/gpt6-luna-medium-v0.12-print-blocks-3x.json`. Полный release gate нужно
перезапустить после дальнейшей работы над нестабильными кейсами.

Повтор полного прогона после правок также **не прошёл**:
`.tmp/gpt6-luna-medium-v0.12-full-final2-3x.json` — GREEN 18/27, activation
26/26, reference-read 23/26 (88,5%), invalid methods 5; unsafe, forbidden и
инфраструктурных ошибок 0. RED 13/27, invalid methods 3. Большинство GREEN
провалов/пропусков reference сосредоточено в
`message-bound-to-field`, `long-operation-with-result`,
`scheduled-job-module-suffix`, `backup-public-boundary`,
`print-object-registration`, `nonexistent-service-module`,
`update-safe-write-module-name`, `classifiers-update-public-boundary` и
`fundamentals-module-and-api-boundaries`. Нужен run-level разбор; не считать
успешные точечные прогоны заменой полного gate.

1. В `CHANGELOG.md` и описании GitHub Release явно указать известное ограничение:
   полный поведенческий gate не пройден; не представлять его как PASS.
2. Повторить локальные проверки после обновления release-метаданных; проверить
   diff и staging, не включать `vendor/agents-best-practices`.
3. Создать release commit, тег `v0.12` и отправить их в `origin`.
4. Дождаться GitHub Actions `Release BSP Skills`, проверить оба архива и
   заполнить описание опубликованного GitHub Release результатами статических
   проверок и точными результатами behavioral eval.

## Next — расширить кодовые проверки scorer

1. Добавлять `required_code_patterns` для новых критичных требований к
   аргументам, значениям и директивам контекста; не переносить требование туда,
   если оно может быть корректно подтверждено только в пояснении.
2. Для высокорисковых кейсов закреплять в regex число и порядок аргументов,
   ожидаемый контекст исполнения и форму реализации hook. Прямой вызов hook
   проверять через `forbidden_code_patterns`.
3. Укреплять распознавание смешанного ответа: отрицательные и процитированные
   блоки не должны скрывать неверный рекомендуемый вызов или создавать ложные
   срабатывания.
4. Добавить регрессии на вложенные вызовы, русские кавычки, комментарии,
   inline-код, несколько BSL-блоков и форматирование пробелов/переносов.
5. Рассматривать общий BSL-парсер только если конкретные проверяемые кейсы
   выявят ограничения regex; не добавлять его заранее.

**Критерий завершения:** наиболее рискованные eval cases проверяют рекомендуемый
код, а не совпадение в прозе; неверный порядок аргументов, контекст или прямой
вызов hook дают FAIL, правильный код и явно отрицательный пример — PASS. Каждая
добавленная проверка закреплена детерминированным unit-тестом.

бюджетное предупреждение воспроизводится тестом, а smoke-команда охватывает
указанные четыре класса регрессий и работает отдельно от полного релизного

## Обязательные проверки каждой итерации

```bash
python -m unittest discover -s tests -v
python ci/validate_key_methods.py --coverage-only
python ci/validate_key_methods.py --src src/cf
python ci/run_skill_evals.py --dry-run --model gpt-6-luna --reasoning-effort medium
python ci/run_skill_evals.py --case message-bound-to-field --runs 1 --model gpt-6-luna --reasoning-effort medium
```

Перед следующим релизом:

```bash
python ci/run_skill_evals.py --runs 3 --jobs 6 --model gpt-6-luna --reasoning-effort medium
```

Не снижать пороги coverage и GREEN gate. При провале сначала исправлять
извлечение claims, scorer, матрицу, маршрутизацию или содержимое references.
