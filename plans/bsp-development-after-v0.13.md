# Развитие единого скила `bsp` после v0.14

**Статус:** действующий план, актуализирован 2026-10-08 после публикации v0.14.
Имя файла сохранено для существующих ссылок. История подготовки v0.12/v0.13 —
в `2026-08-30-bsp-skill-improvements.md`; опубликованный v0.14 и ограничения —
в `../reports/bsp-skills/v0.14-published-verification.md` и
`../reports/bsp-skills/v0.14-release-candidate-readiness.md`.

## Отправная точка

- Поставляется **один** `skills/bsp/`: короткий маршрутизатор, 24 тематических
  `references/`, скрипт `scripts/bsp_api.py`. Содержимое `.agents/skills/` —
  отдельные, неизменённые сторонние скилы для разработчиков Pi; в релиз BSP
  они не входят и не служат источником сведений об API БСП.
- v0.14 опубликован; скачанные архивы побайтно соответствуют проверенному
  кандидату. Guided-корпус: GREEN 27/27 по большинству, 77/81 отдельных
  запусков; отдельный activation/boundary-корпус: 6/6 и 16/18. Оба gate PASS,
  без invalid/unsafe/forbidden/infra в GREEN. Это результаты разных профилей,
  их не складывать и не сравнивать с v0.13 как причинное улучшение качества.
- API coverage — 664/664 утверждения, 24/24 references; семантическая проверка
  по выгрузке 3.1.11 — 0 ERROR / 0 WARN. Совпадение сигнатуры/региона само
  по себе не доказывает поведение метода и не является компиляцией BSL.
- Уже добавлены три отрицательные задачи обычного BSL/платформы, две задачи
  самостоятельной активации и отдельная граница другой версии. Их корпус и
  матрица находятся в `evals/activation-*.json`, отдельно от guided gate.
  Activation-корпус покрывает только 2/24 references; расширение остаётся P1.
- Калибровка scorer и исправления маршрутов v0.14 завершены для подтверждённых
  причин, с парными регрессиями без снижения порогов. Единичные пропуски чтения
  и неподтверждённая сигнатура другой версии остались FAIL в исходных отчётах.

## P0 — чистая и воспроизводимая база сравнений

**Статус на 2026-10-08: не закрыт.** Добавлен
`ci/probe_eval_isolation.py`: native preflight без model turns, с отдельным
credential-free `CODEX_HOME`. Он сравнивает catalog/config/permissions в RED,
GREEN и после удаления staged `bsp`; неожиданные различия и ошибки discovery
дают отказ. Положительная проба и отрицательный контроль с посторонним
проектным скилом проверены; результат — в
`../reports/bsp-skills/p0-native-preflight-after-v0.14.md`.

Это **отдельный app-server профиль**, а не наблюдение реальных `exec`-процессов.
PASS preflight не закрывает P0 и не меняет ограничения релизов.
Добавлен opt-in `--transport native` / профиль `native-runtime-v1`:
per-run inventory до/после turn в одном процессе, PID/thread/turn binding,
post-cleanup RED snapshot, отдельный isolation gate, schema v5 и resume
fingerprints helpers/account identity. Credentials используются только в
защищённом disposable home; исходный auth.json не меняется. Native helper
покрыт unit-тестами; до реального smoke/baseline **P0 не закрывать**.
Следующий шаг — выполнить этот smoke, исправлять только подтверждённые причины,
фиксировать коммиты и перезапуски в отдельном runtime-отчёте. Новый профиль
не объявлять эквивалентным историческому `exec`.

**Зачем:** проектные `.agents/skills/` могут обнаруживаться агентом как в RED,
так и в GREEN, если рабочий каталог находится внутри этого репозитория.
`--ignore-user-config` не доказывает изоляцию от проектных скилов. Нельзя
приписывать их возможное влияние скилу `bsp`.

1. Для поведенческого baseline и следующих сравнений использовать `--dir`
   с **отдельным потребительским Git-корнем вне этого репозитория**. В нём нет
   `bsp3111_md/`, `src/cf/`, заранее установленного `bsp` и иных проектных
   скилов, влияющих на задачу. README и другие файлы fixture не должны
   рассказывать агенту о RED/GREEN, staging и расположении скила; проверить
   чтение этих файлов в обеих трассах. Записать состав окружения и host plugins.
2. RED и GREEN проводить на одних модели, effort, задаче и рабочем каталоге;
   единственное запланированное отличие — staged `bsp` в GREEN. Сохранять
   fingerprint скила, runner, корпуса и матрицы; проверять доступный
   skill catalog, а не только факт чтения файла. Инфраструктурные ошибки не
   пересчитывать в успешные ответы. Не сравнивать результаты разных моделей,
   изменений evaluator, assisted и guidance-free профилей как один эксперимент.
3. Для нового baseline использовать опубликованный распакованный v0.14
   либо точно зафиксированную кандидатную ревизию. Сравнения с v0.13 — только
   при отдельной задаче, с явным описанием различий окружения и evaluator.
   Не объявлять исторический PASS равнозначным новому результату.

**Готово, когда:** у нового baseline есть отчёт и описание изоляции;
контрольный RED не видит `bsp` в каталоге доступных скилов, GREEN видит
только staged `bsp` как дополнительный доменный скил; в обоих нет ошибок
окружения. Изменение baseline само по себе не требует правки `SKILL.md`.

## P1 — границы активации и покрытие поведения

1. Три разные отрицательные задачи уже добавлены в v0.14. Сохранять проверки
   правильного ответа и отсутствия активации; расширять границы при наблюдаемом
   пробеле, а не заново добавлять тот же набор. Показывать ложные активации
   отдельно от показателя активации положительных сценариев.
2. Граница **БСП другой версии** уже добавлена; в v0.14 один из трёх ответов
   корректно остался FAIL за неподтверждённую точную сигнатуру. Удерживать
   требование не выдавать API 3.1.11 за проверенный API другой версии. Это не
   обязательно `should_trigger=false`: допустимо включить `bsp` для распознавания
   границы. Данные `bsp321_md/` не переносить без явной проверки и задачи на
   сравнение; уточнять ожидание кейса только при доказанном дефекте критерия.
3. Дать второй сценарий наиболее рискованным reference (например,
   `fundamentals.md`, `base-common.md`, `print-reports.md`) и одной
   сквозной задаче с двумя темами. Не размножать по кейсу на каждый метод:
   проверять выбор раздела, прикладной контекст, публичный/служебный API,
   hook versus вызов и правильное поведение.
4. Для каждого добавления обновлять корпус и его матрицу **вместе**:
   guided — `evals/cases.json` / `evals/reference-matrix.json`; самостоятельная
   активация и отрицательные границы — `evals/activation-cases.json` /
   `evals/activation-reference-matrix.json`. Вначале прогонять точечный RED/GREEN;
   затем повторять затронутые сценарии и полную матрицу перед релизом.

**Готово, когда:** новые пограничные кейсы воспроизводимо отличают верный
ответ от правдоподобной ошибки; матрица проходит `--dry-run`; в полном
GREEN-прогоне все новые и прежние кейсы проходят действующий gate. Число
кейсов — не самоцель; в отчёте отдельно видны false-positive активации.

## P2 — разбор ошибок качества без ослабления gate

1. Калибровки v0.14 не считать будущей работой повторно. Для оставшихся и
   новых одиночных отказов различать ошибку ответа, пропуск чтения reference
   и false negative scorer. При обращении к историческим отказам v0.13
   сначала проверить, исправлена ли причина в v0.14 и есть ли регрессия.
   Сырые трассы в `.tmp/` — локальные артефакты; если их нет, воспроизвести
   случай, а не утверждать, что он устранён.
2. На каждый подтверждённый дефект scorer сделать пару регрессий:
   **правильный ответ принимается; похожий неверный отвергается**. Для
   расхождения в смысле ответа, не выражаемого надёжным шаблоном, использовать
   выборочное независимое ревью с проверкой по источнику, а не один общий
   балл LLM-judge. Реальные неправильные вызовы, служебные методы и прямые
   вызовы hook по-прежнему блокировать детерминированно.
3. Править самый узкий слой: reference/маршрут — при реальной ошибке агента;
   scorer — при доказанном false negative; кейс — если неверно сформулировано
   ожидание. Не исправлять провал уменьшением `--min-claims`, `--min-files`,
   `--min-coverage` или GREEN-порогов.

**Готово, когда:** каждая исправленная причина имеет unit-регрессию и
свежий поведенческий результат; прежние реальные ошибки по-прежнему FAIL.

## P3 — проверяемость поведенческих правил при авторинге

1. Пилотировать **внутреннюю** таблицу для нескольких правил с повышенным
   риском (например, привязка сообщения к полю, права доступа, МЧД, хуки
   печати): утверждение → документ БСП 3.1.11 → подтверждение сигнатуры,
   региона и контекста по `src/cf/` → сценарий/reference → результат проверки.
2. При расхождении документации и исходника явно фиксировать расхождение и
   его влияние на рекомендацию; по вопросу назначения сначала изучать
   документацию, затем исходник. Не считать совпадение имени метода
   доказательством поведения. Если пилот не обнаружит проблемы, не строить
   реестр всех API-утверждений ради самого реестра.
3. Держать evidence в материалах разработчика, **не** в поставляемом скиле:
   установленный `bsp` должен работать без локальной документации/выгрузки.

**Готово, когда:** выбранные нюансы можно независимо проверить по двум
локальным источникам, противоречия не замолчаны, формат не увеличил роутер
и не сделал скил зависимым от файлов разработчика.

## P4 — цена, устойчивость и подготовка будущего релиза

- Использовать уже собираемые токены и повторы; при заметном росте стоимости
  при том же качестве добавить диагностический разрез по кейсу/reference и
  предупреждение о бюджете. Не превращать стоимость в основание для
  принятия неправильного ответа. Проверять эффективность чтения сценария
  экспериментом, а не универсальным лимитом длины файла.
- Поддерживать быстрый smoke из нескольких разных границ (активация,
  публичный/служебный метод, hook или аргументы, отрицательный случай), но
  **не заменять** им полный RED/GREEN 3 × перед релизом. Результаты другой
  модели хранить отдельно.
- Не внедрять без наблюдаемой потребности autonomous self-modification,
  hosted-агентов, BDI, KV-cache/latent-briefing, постоянную память и
  универсальный парсер BSL. Сторонние `.agents/skills/` не переписывать
  под `bsp` и не включать в архив скила.

## Порядок работы и контроль

Итерация: выбрать **одну** наблюдаемую проблему → сохранить baseline →
сделать минимальную правку с негативной регрессией → точечный RED/GREEN →
проверить, что контрольные сценарии не деградировали. При изменении scorer,
корпуса или порогов фиксировать границу сравнимости; изменения критериев
рассматривать отдельно от улучшения самого reference.

После изменения `skills/bsp/` или валидатора выполнить:

```bash
python -m unittest discover -s tests -v
python ci/validate_key_methods.py --coverage-only
python ci/validate_key_methods.py --src src/cf
python ci/run_skill_evals.py --dry-run
```

Если `src/cf/` отсутствует — выполнить первые две команды и сообщить, что
семантическая проверка по выгрузке не выполнена. Для поведенческой проверки
сначала сделать `--case message-bound-to-field --runs 1`, перед релизом —
`--runs 3 --jobs 6` (тот же `--dir` из P0). Зафиксировать модель и effort,
версию артефакта, параметры и ограничения проверки в отчёте; результаты
разных моделей не усреднять. Не публиковать релиз как побочный эффект плана.
