## Проверка отказов на сохранённых трассах

Для диагностики использованы оригинальные `.tmp/p0-isolated-baseline-3x.json`, `.tmp/p0-isolated-smoke.json` и `.tmp/canonical-v0.13-r2-full-3x.json` вместе с `.response.md`. Оригинальные отчёты **не** переписаны и quality failures не заменялись повторами.

Правки scorer затронули `ci/run_skill_evals.py` и `tests/test_run_skill_evals.py`. Независимая попытка опровергнуть исправление обнаружила регрессию: «Например, такой код использовать нельзя» перестало маркировать предшествующий блок как отрицательный. Добавлена сначала красная регрессия, затем точное правило для указания на «такой код/пример/вызов»; ошибочный блок вновь исключается, а соседние примеры ошибок по-прежнему не скрывают рекомендованный код. Все 100 unit-тестов, API coverage (663/663), семантическая сверка (0 ERROR / 0 WARN) и eval `--dry-run` прошли. После финального исправления точечный RED/GREEN `message-bound-to-field` 1× дал GREEN 1/1, activation/reference 1/1 (`.tmp/green-debug-final-message-1x.json`). Перепроверка 81 GREEN-ответа из исходного P0 новым scorer не изменила ни одного verdict; перепроверка архивной v0.13 GREEN-матрицы поменяла только backup #1. Для RED replay изменились `save-attached-file-public-boundary` #3 (v0.13) и `sms-public-wrapper-not-hook` #2 (P0): код раньше ошибочно отбрасывался; их исходные ответы и причинность необходимо рассматривать отдельно. **Replay не является новым модельным прогоном**, статистику прежнего выпуска не пересчитывать.

## Отдельная проверка prompting / активации

Промпт агенту в runner — значение поля `task` из `evals/cases.json` без копирования `required_patterns`/`forbidden_patterns` в пользовательский запрос. Отдельно runner задаёт Windows-инструкцию по чтению UTF-8 файлов; она описывает инструмент, а не API БСП. Metadata staged скила и его references видны только GREEN по design. В `skills/bsp/agents/openai.yaml` есть прямой стартовый prompt «Используй $bsp…», но `build_cdx_command` не добавляет его к `case.task`: не приписывать UI-метаданные проверяемому runner без дополнительного доказательства.

Независимый read-only аудит 27 `task` в `evals/cases.json` показал: **26/27** помечены как positive, **25/27** буквально содержат «БСП 3.1.11» (исключения — `lock-form-fields`, `plain-bsl-no-bsp`); **14/27** включают проверку совета вида «Коллега предлагает…» и часто уже называют ошибочный `Модуль.Метод`. Среди явно направляющих — `message-bound-to-field` (параметры `КлючДанных`, `Поле`, `ПутьКДанным` и запрет платформенной альтернативы), `connected-command-hook-boundary` (имя хука, состав шагов и прямой запрет вызова), `fundamentals-module-and-api-boundaries` (готовые границы API), `dedup-replace-links-public-boundary`, `classifiers-update-public-boundary`. Задачи `long-operation-with-result` и `scheduled-job-module-suffix` конкретизируют библиотеку, но меньше подсказывают алгоритм: назвать БСП по версии уместно, однако это всё равно прямой сигнал для активации. Единственный отрицательный `plain-bsl-no-bsp` явно запрещает библиотеки и слишком далёк от позитивных по словарю, чтобы измерять false positives на пограничных задачах. Ни один task не заставляет открыть конкретный reference-файл по пути; это решение GREEN проверяется трассой чтения. Таким образом, текущий корпус прежде всего измеряет **использование скила при явном BSP/API-контексте**, а не самостоятельное распознавание потребности в нём.

Контрольный consumer-проект первоначально содержал README с буквальной подсказкой о RED/GREEN и пути `.agents/skills/bsp`; RED действительно прочитал его. Этот **наш** fixture-дефект отмечен в `p0-isolated-baseline-after-v0.13.md`, README заменён нейтральным. Старый baseline нельзя называть полностью blind или использовать как доказательство чистоты activation. С нейтральным README и прежней задачей `message-bound-to-field` повторный 1× RED/GREEN прошёл GREEN 1/1 и прочёл reference: `.tmp/p0-neutral-readme-message-1x.json`.

Для диагностического сравнения созданы **две незакоммиченные** вариации `task`, без имён методов, parameter names и описания последовательности (копия корпуса: `.tmp/prompt-neutral-cases.json`):

- `message-bound-to-field`: «В конфигурации с БСП 3.1.11 при записи заказа нужно остановить запись, если не указан контрагент, и показать сообщение рядом с соответствующим полем формы. Как реализовать проверку? Приведи короткий пример на BSL.»
- `connected-command-hook-boundary`: «В конфигурации с БСП 3.1.11 для заказов клиентов нужна подключаемая команда „Сверить оплату“, которая видна только после проведения документа. Как правильно её добавить? Приведи пример BSL и укажи, где разместить реализацию.»

В `.tmp/prompt-neutral-diagnostic.json` оба RED не читали скил, оба GREEN прочитали staged скил и соответствующий reference (**2/2**; по одному запуску, не статистическая гарантия). Прежний scorer дал GREEN 0/2: для первого требовал незапрошенные `КлючДанных`, `ПутьКДанным` и обсуждение их конфликта; для второго — конкретный обработчик `СверкаОплатыКлиент.ВыполнитьСверку` и буквальное предупреждение о прямом вызове хука, хотя формулировка этого не требовала. **Эти FAIL нельзя интерпретировать как дефект ответов без отдельной рубрики**, равно как 2/2 активаций нельзя экстраполировать на весь корпус. Нельзя сравнивать gate этого диагностического корпуса с основным.

Третий диагностический вариант той же задачи **без упоминания БСП** (`.tmp/prompt-no-bsp-cases.json`, `.tmp/prompt-no-bsp-diagnostic.json`) дал GREEN activation/reference 0/1 и платформенный ответ с `Новый СообщениеПользователю`; это ожидаемое поведение для обычной 1С-задачи, а не доказательство неспособности скила. Старый scorer вновь выдал FAIL, потому что сохранённые от *другой* задачи критерии требовали BSP-вызов и запрещали платформенный объект. Ещё один вариант **без букв «БСП», но с доменным термином «подключаемая команда»** (`.tmp/prompt-connected-implicit-diagnostic.json`) дал GREEN activation/reference 1/1; прежний scorer снова дал FAIL по унаследованным более узким требованиям. Это единичные пробы, не оценка частот. Контроли подчёркивают необходимость явно различать задачи с библиотекой и без неё и иметь отдельные корректные ожидания.

Рекомендация: не снижать существующий gate и не переименовывать старые guided-сценарии в unassisted. Развести (а) подробные интеграционные сценарии с явно заданными требованиями и (б) отдельный набор нейтральных user tasks для оценки самостоятельной активации, правильного выбора reference и качества ответа по независимым ожиданиям; в него включить несколько отрицательных и пограничных задач. Для новых/перенесённых случаев синхронно обновлять `evals/cases.json` и `evals/reference-matrix.json`. Blind fixture никогда не должен рассказывать агенту о механике eval.
