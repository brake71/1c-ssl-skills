## 1. ANSI reader diagnostic — подтверждён, исправлен

Реальный `pwsh -NoProfile -NonInteractive` в пустом tempfile:
`Get-Content -Encoding utf8 '.agents/skills/bsp/references/prefixes.md'; echo README.md`.
Общий exit 0; stdout содержит README.md, stderr — цветной `Get-Content:` и
`Cannot find path`. До изменения raw output давал evidence, после удаления
ANSI тот же output не давал evidence. Это неполнота новой защиты, не новая
регрессия относительно v0.14.

Исправление: ANSI CSI удаляется только из копии output для распознавания
reader diagnostic. Original output/commands, receipts, decode checks и gates
не меняются. Portable регрессии используют настоящий формат PowerShell,
цвет внутри pathname и controls: успешное чтение, другой target/.bak и
независимый retry. Наблюдался RED, затем GREEN. Реальный pwsh подтвердил
отказ для missing path с ANSI и успех controls; успешный fixture в этой
проверке ASCII, чтобы не смешивать баг с console output code page.

В первой итерации новых model runs не было; во второй — только свежие
отдельные отчёты. Изменившийся runner SHA не позволяет resume исторического
отчёта новым кодом; его результаты не обновляются задним числом.

### Проверка receipt и последующие resume

Receipt — отдельный ручной аудит; isolation gate доказывает только свои
catalog/config/account/permissions invariants. Обычные consumer bytes не
входят в runner resume fingerprints, даже при неизменном workdir path.

Для следующего baseline до RED и после cleanup сохранять sorted manifest
`relative path / size / SHA256` ordinary files, отдельно аудит их содержания и
actual reader output. Исключать `.git` metadata явно; staged `.agents/skills/bsp`
сравнивать отдельно существующим inventory gate, а не исключать все `.agents`.
Зафиксировать исключения и временные границы каждого manifest.

Перед resume сравнить текущий fixture с исходным manifest. При различиях
не приписывать старые turns новому fixture. Если исходного manifest нет,
не приклеивать новый snapshot к старому PASS: такой resume подтверждает
только native inventory/control, не историческую неизменность fixture.
Новый полный proof потребует отдельного baseline с предварительным manifest,
а не quality retry существующего FAIL. Этот критерий пока не автоматизирован;
не предполагается, что нынешний runner отклоняет изменения README.

Чтобы независимо проверить сохранённые witnesses без модели:

```python
import hashlib, json
from pathlib import Path
receipt = json.loads(Path('reports/bsp-skills/v0.14-0749271-consumer-fixture-audit.json').read_text(encoding='utf-8'))
for report in receipt['reports']:
    assert hashlib.sha256(Path(report['report']).read_bytes()).hexdigest() == report['report_sha256']
    for phase in report['phases'].values():
        witness = phase['witness']
        if witness is None:
            continue
        path = Path(witness['artifact'])
        assert hashlib.sha256(path.read_bytes()).hexdigest() == witness['artifact_sha256']
        event = json.loads(path.read_text(encoding='utf-8').splitlines()[witness['jsonl_line'] - 1])
        assert event['type'] == 'item.completed'
        assert event['item']['type'] == 'command_execution'
        assert event['item']['exit_code'] == 0
        print(path, event['item']['command'], event['item']['aggregated_output'])
```

Counts — результаты ограниченного локального обзора всех JSONL этих пяти
corpora; для самостоятельной проверки конкретного вывода receipt содержит
witnesses и checksums, а не обещание восстановить всю history без артефактов.

### Разбор actual traces и оставшиеся причины

- Все три guided API-review trace реально читали `data-exchange.md` native rg
  с контекстом; положительный результат не получен снятием reference requirement.
  В counterpart standalone platform request ни один GREEN не читал BSP.
- Три hook ответа проверены по actual response: четыре параметра exported hook,
  требуемый Вид, штатный visibility API и hook-vs-call distinction присутствуют.
  Reader outputs содержат сценарий. Это контроль 3/3 этой выборки, не доказательство
  универсального устранения прежнего 2/3 или проверка исполнения BSL в конфигурации.
- Caption 3/3 корректен без чтения BSP; прежний false activation 1/9 остаётся
  историческим наблюдением, не пересчитывается в 0/9 из новой выборки.
- Единственный GREEN FAIL — standalone exchange #1: ответ рекомендует
  `ПланыОбмена.ЗаписатьИзменения` и не содержит требуемую регистрацию.
  Trace не содержит command executions/BSP reads. Это платформенная ошибка
  вне продукта BSP integration, а не reader/inventory failure. FAIL сохранён;
  навязывать BSP activation или включать платформенный ответ в skill prompt
  означало бы нарушить принятую границу. Остальные два GREEN ответа проходят.
- Activation coverage 2/24 остаётся roadmap; negative-only targeted corpus
  не измеряет положительную implicit activation всех references.
